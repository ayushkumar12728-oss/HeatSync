 2. WHAT YOU ARE INSTALLING (PROJECT OVERVIEW)
--------------------------------------------------------------------------------

The project is an AI-powered Urban Digital Twin for monitoring, predicting
and simulating Urban Heat Island (UHI) effects in Bhubaneswar, Odisha, India.
It takes raw satellite imagery and open data, turns them into a 100 m
prediction grid, trains an XGBoost machine-learning model that predicts land
surface temperature (LST), and serves the results through a web dashboard
called "HeatSync".

The complete system has four runtime pieces:

  1. BACKEND API  - a FastAPI (Python) service on port 8000. It serves the
     trained model, predictions, scenarios, GIS layers, monitoring reports and
     the optional AI (Nemotron) explanations. It can run two ways:
        (a) with Docker (docker compose)  - recommended, easiest
        (b) directly from a Python virtual environment - local mode
  2. FRONTEND     - a React + Vite web dashboard on port 5173 (development).
     It is the 3D map + analytics + scenario simulator UI.
  3. DATABASE     - PostgreSQL with the PostGIS extension (port 5432).
     OPTIONAL: the API is "artifact-first" and works without a database.
  4. DATA + MODEL - the pipeline outputs (data/) and the trained model
     (models/best_model.pkl). These already exist in the repository folder you
     have (they are NOT stored on GitHub - see section 25).

The important design decision to understand: the backend reads everything from
files on disk (data/ and models/). The database is an optional extra. This
means the system can run with only two processes: FastAPI (port 8000) and
Vite (port 5173).

IMPORTANT: the frontend is NOT part of the docker-compose stack. You always
start the frontend separately with `npm run dev` (section 9), no matter how
the backend is started.

 3. SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------

The data-flow of the complete system (verified from the source code):

    Browser (HeatSync dashboard)
        |
        v
    React + Vite (frontend/)              port 5173 (dev)
        |
        v   /api requests through the Vite dev proxy (vite.config.js)
            (development) or directly to VITE_BACKEND_API_URL (production)
        v
    FastAPI backend (backend/)            port 8000
        |
        +--- XGBoost model (models/best_model.pkl)  - LST prediction
        +--- GIS engine outputs (data/processed, data/raw/osm) - map layers
        +--- Scenario engine (ai-engine scenario simulator) - "what-if" runs
        +--- AI / Nemotron (NVIDIA NIM, OpenAI-compatible) - explanations
        +--- PostgreSQL / PostGIS (database/) - OPTIONAL PostGIS mode
        +--- GIS datasets (data/, frontend/public/) - layers, overlays, DEM

Layers of the stack in one line:

    Browser -> React + Vite -> Vite /api proxy -> FastAPI
        -> XGBoost model | GIS engine | Scenario engine | AI/Nemotron
        -> PostgreSQL/PostGIS (optional) | GIS datasets

Key facts verified from the code:

  - vite.config.js proxies every `/api` request from the frontend to
    http://localhost:8000 during development, so the browser never calls the
    backend directly and CORS is not an issue in development.
  - In a production build, the frontend uses VITE_BACKEND_API_URL (default
    http://localhost:8000/api).
  - The backend (backend/main.py) mounts routers for: health, data,
    prediction, simulation, explainability, dashboard, monitoring,
    environment, model, ai, city, routing.
  - The trained model is loaded lazily on the first prediction request and
    reused for every later request (backend/services/serving.py).


--------------------------------------------------------------------------------
 4. FOLDER-BY-FOLDER EXPLANATION
--------------------------------------------------------------------------------

  frontend/         The HeatSync web dashboard: React 19 + Vite 8 + MapLibre
                    GL (3D map) + Leaflet + Chart.js. `public/` contains the
                    browser-safe GIS assets (OSM web layers, PNG overlays,
                    terrain tiles). `src/services/` contains the API clients.

  backend/          The FastAPI service. `main.py` is the application
                    factory, `api/` holds the routers, `services/` holds
                    model serving, simulation, Nemotron, catalog, database,
                    `config/settings.py` reads the UDT_* environment
                    variables, `schemas/` defines request/response models.

  ai-engine/        The UHI machine-learning pipeline: leakage detection,
                    5-fold cross-validation, 6-model comparison, Optuna
                    hyper-parameter tuning, final XGBoost training, ONNX
                    export, SHAP explainability, sensitivity scenarios and
                    full-grid prediction. Entry point: `ai-engine/main.py`.

  gis-engine/       The remote-sensing data pipeline: downloads and processes
                    Sentinel-2 (NDVI, green cover, vegetation density, land
                    cover), Landsat 8/9 (LST, heat classes), DEM (elevation,
                    slope, aspect, hillshade, contours), NASA POWER weather
                    and air quality (AQI). `feature_engineering/` builds the
                    100 m ML training grid. Entry point: `gis-engine/main.py`.

  scenario-engine/  A standalone simulation library (tree canopy, cool roofs,
                    green corridors, comparison) used by the frontend's
                    microclimate simulator. The API scenario engine actually
                    delegates to the ai-engine's ScenarioSimulator.

  database/         Optional PostgreSQL/PostGIS schema (`schema/init.sql`),
                    SQL migrations (`migrations/0001_initial_schema.sql`),
                    a migration runner (`migrate.py`) and an artifact loader
                    (`seed/load_artifacts.py`).

  deployment/       Dockerfile (`docker/Dockerfile`), sample nginx reverse
                    proxy (`nginx/nginx.conf`), environment templates
                    (`env/`) and a deployment script (`deploy.sh`).

  data/             ALL pipeline outputs: raw downloads, processed rasters,
                    the 53,802-cell training dataset, predictions and AI
                    engine reports. This folder is NOT committed to GitHub.

  models/           The trained model: `best_model.pkl` (used for inference)
                    and `best_model.onnx` (informational). NOT committed.

  tests/            The pytest suite (backend API, serving, end-to-end).

  docs/             Project documentation (this guide lives here too).

  scripts/          Utility scripts (browser test, overlay asset generation,
                    scenario-cell prewarming). See scripts/README.md.

  docker-compose.yml   The local Docker stack: backend + optional PostGIS.
  requirements.txt     Python runtime dependencies (backend + engines).
  requirements-dev.txt Python development dependencies (pytest, ruff, ...).
  .env.example         Template for the backend environment variables.
  boundary.geojson     The Bhubaneswar study-area boundary (used by every
                       pipeline stage and the API).
  Makefile             Developer shortcuts (requires `make`; optional).

 5. SYSTEM REQUIREMENTS
--------------------------------------------------------------------------------

These are the ACTUAL requirements, derived from the repository (Dockerfile,
docker-compose.yml, requirements.txt, package.json, README.md and the
installed packages). Versions that the repository does not pin are marked
"VERIFY IN YOUR ENVIRONMENT" - install the recommended version and confirm.

REQUIRED (you cannot run the system without these):

  - Windows 10 or 11 (64-bit)
  - Python 3.11 or newer
      * The backend Docker image is built FROM python:3.11-slim.
      * docs/setup.md says: "Developed on 3.11; verified on 3.14".
      * The environment on the machine where this guide was written used
        Python 3.14.6 and the full dependency set installed and ran fine.
      * Recommendation: Python 3.11 or 3.12 (matches the Docker image); 3.13
        or 3.14 also work. Do not use Python 3.9 or older.
  - Node.js and npm
      * README.md says Node v18+ / npm v9+.
      * BUT the pinned Vite 8.2.x declares "engines": node "^20.19.0 ||
        >=22.12.0" (checked in frontend/node_modules/vite/package.json).
        So the REAL minimum for this repository is Node 20.19+ (or 22.12+).
      * Recommendation: install the current Node.js LTS (22.x) or Node 24.x,
        which satisfies both the README and Vite. The machine where this
        guide was written used Node v24.18.0 with npm 11.4.2.
  - Git (to clone / update the repository)
  - Docker Desktop with the WSL2 backend - REQUIRED for the docker compose
    path (section 11). If you choose the local Python mode (section 18) you
    do not need Docker, but the QUICK START in section 17 uses Docker.
  - An internet connection for the first-time installs (Python packages, npm
    packages, Docker images) and for the optional live data sources.
  - Disk space: at least 10 GB free. The full data/ folder in this repository
    is roughly 1.2 GB, the Python environment ~1-2 GB, node_modules ~0.5 GB,
    and Docker images ~2-3 GB.
  - A modern browser: Chrome, Edge or Firefox (the 3D map uses WebGL via
    MapLibre GL; enable hardware acceleration).

RECOMMENDED (not strictly required, but the pipeline is much more pleasant):

  - 8 GB RAM minimum, 16 GB recommended. Training XGBoost on 53,802 rows is
    the heaviest step; the machine where this guide was written used 16 GB.
  - A multi-core CPU (the AI engine uses n_jobs = number of cores - 1).
  - Windows Terminal (nicer than the old console, same commands).
  - Git for Windows (comes with Git Bash, useful for the Makefile targets).

OPTIONAL:

  - A CUDA-capable NVIDIA GPU - XGBoost uses the GPU automatically when one
    is available; set AIE_NO_GPU=true in .env to force CPU training.
  - PostgreSQL 14+ with PostGIS installed natively - only if you want the
    database mode without Docker.
  - conda / miniconda - only if `pip install rasterio geopandas` fails on
    Windows (see section 8, GDAL note).
  - WSL2 - required by Docker Desktop on Windows; Docker Desktop installs it
    for you. Also useful for running the Makefile targets.

Verify your installed versions with (see section 6 for details):

    python --version
    node --version
    npm --version
    git --version
    docker --version
    docker compose version

 6. INSTALL THE REQUIRED SOFTWARE

Install these in order. Each subsection gives the official install method,

 6.1 Git
--------------------------------------------------------------------------------
Official source: https://git-scm.com/download/win

COMMAND:
> winget install --id Git.Git -e --source winget
(or download the installer from git-scm.com and click through it)

WHERE:
> PowerShell (run as normal user; winget is built into Windows 10/11)

PURPOSE:
> Installs Git, needed to clone the repository and (later) update it.

VERIFY:
COMMAND:
> git --version
EXPECTED OUTPUT:
> git version 2.xx.x.windows.x

COMMON ERRORS:
  - "'git' is not recognized as the name of a cmdlet..."
    CAUSE: Git not installed or not on PATH. Reinstall and tick
    "Add Git to PATH" / restart PowerShell.

--------------------------------------------------------------------------------
 6.2 Python
--------------------------------------------------------------------------------
Official source: https://www.python.org/downloads/windows/

COMMAND:
> winget install --id Python.Python.3.12 -e --source winget
(or download the installer from python.org)

WHERE:
> PowerShell

PURPOSE:
> Python runs the FastAPI backend and the GIS / AI / scenario engines.

IMPORTANT (two Windows gotchas):
  1. During the python.org installer, tick "Add python.exe to PATH".
  2. If you type `python` and the Microsoft Store opens, you hit the Windows
     "App execution alias". Disable it: Settings -> Apps -> Advanced app
     settings -> App execution aliases -> turn off "python.exe" / "python3.exe".

VERIFY:
COMMAND:
> python --version
EXPECTED OUTPUT:
> Python 3.12.x

If `python` is not on PATH but the `py` launcher is, use:

COMMAND:
> py -3.12 --version
> py -3.12 -m venv ...   (use "py -3.12 -m venv" instead of "python -m venv")

COMMON ERRORS:
  - "Python was not found; run without arguments to install from the
    Microsoft Store"  ->  Store alias problem, see IMPORTANT above.
  - "'python' is not recognized..." -> not on PATH; reinstall with the
    "Add to PATH" option and restart PowerShell.

 6.4 Docker Desktop (needed for the Docker path)
--------------------------------------------------------------------------------
Official source: https://www.docker.com/products/docker-desktop/

COMMAND:
> winget install --id Docker.DockerDesktop -e --source winget

WHERE:
> PowerShell

PURPOSE:
> Docker Desktop provides Docker Engine + Docker Compose on Windows. It runs

After installation:
  - Launch "Docker Desktop" from the Start menu once, accept the license and

VERIFY:
COMMAND:
> docker --version
EXPECTED OUTPUT:
> Docker version 2x.x.x, build xxxxxx

> docker compose version
EXPECTED OUTPUT:
> Docker Compose version v2.x.x   (v5.3.1 on the reference machine)

COMMON ERRORS:
  - "'docker' is not recognized..." -> Docker Desktop is not installed, or

  - "error during connect: This error may indicate that the docker daemon is
    not running" -> Docker Desktop is installed but not started. Start it
    from the Start menu and wait for "Engine running".
  - WSL errors during install -> see 6.5.

--------------------------------------------------------------------------------
 6.5 WSL2 (required by Docker Desktop)
--------------------------------------------------------------------------------
Official source: built into Windows (Microsoft Store "Windows Subsystem for
Linux" or the `wsl --install` command).

COMMAND:
> wsl --install

WHERE:
> PowerShell (Administrator)

PURPOSE:
> Installs the Windows Subsystem for Linux and sets WSL2 as the default
> version. Docker Desktop uses WSL2 as its Linux backend. If Docker Desktop
> already installed WSL2 for you, this step is already done.

VERIFY:
COMMAND:
> wsl --status
EXPECTED OUTPUT:
> Default Version: 2   (and a line about the default distro)

If it shows "Default Version: 1", fix with:

COMMAND:
> wsl --set-default-version 2

COMMON ERRORS:
  - "WSL 2 requires an update to its kernel component" -> run `wsl --update`
    (as Administrator), then restart.
  - Virtualisation is not enabled in the BIOS -> enable "Intel VT-x" /
    "AMD-V" in the firmware settings, or enable "Virtual Machine Platform"
    in Windows Features, then reboot.

 8. CREATE THE PYTHON ENVIRONMENT
--------------------------------------------------------------------------------

The project uses a virtual environment named `.venv` in the project root.
A `.venv` folder already exists on the reference machine; on a fresh machine
you create it yourself.

--------------------------------------------------------------------------------
 8.1 Create the virtual environment
--------------------------------------------------------------------------------
COMMAND:
> python -m venv --system-site-packages .venv

WHERE:
> PowerShell, in the project root (F:\urban-digital-twin)

PURPOSE:
> Creates an isolated Python environment inside the project folder so the
> project's packages never conflict with other Python programs on your
> computer. `--system-site-packages` lets the environment reuse any
> geospatial wheels already installed on the system - recommended on
> Windows, and it matches what the project's Makefile does.

EXPECTED OUTPUT:
> (no output on success; the folder .venv\ appears)

--------------------------------------------------------------------------------
 8.2 Activate the environment
--------------------------------------------------------------------------------
COMMAND:
> .\.venv\Scripts\Activate.ps1

WHERE:
> PowerShell, in the project root

PURPOSE:
> Switches the current PowerShell session to use the .venv Python. After
> activation your prompt shows a (.venv) prefix.

POSSIBLE PROBLEM - PowerShell execution policy:
If you see an error like:
    "...cannot be loaded because running scripts is disabled on this system."
Fix it (one time, safe):

COMMAND:
> Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

WHERE:
> PowerShell

PURPOSE:
> Allows locally-created scripts (like Activate.ps1) to run in your user
> account without changing system-wide security.

VERIFY the environment is active:
COMMAND:
> python --version
EXPECTED OUTPUT:
> Python 3.11.x (or newer)

If you prefer not to change the execution policy, you can run every Python
command with the explicit interpreter path instead of activating:

COMMAND:
> .\.venv\Scripts\python.exe --version

(All commands in this guide that say `python ...` assume the environment is
activated. Replace `python` with `.\.venv\Scripts\python.exe` if you did not
activate.)

--------------------------------------------------------------------------------
 8.3 Upgrade pip
--------------------------------------------------------------------------------
COMMAND:
> python -m pip install --upgrade pip

WHERE:
> PowerShell, .venv activated, project root

PURPOSE:
> Ensures the package installer is current before installing dependencies.

 8.4 Install the Python dependencies
--------------------------------------------------------------------------------
The repository defines exactly two requirement files:

  requirements.txt       - everything needed to RUN the backend and the
                           engines (FastAPI, XGBoost, geopandas, rasterio,
                           SHAP, onnx, sqlalchemy, ...).
  requirements-dev.txt   - development/test tools: pytest, pytest-cov,
                           httpx, ruff. It starts with `-r requirements.txt`,
                           so installing it also installs the runtime deps.

COMMAND:
> pip install -r requirements.txt

WHERE:
> PowerShell, .venv activated, project root

PURPOSE:
> Installs the runtime dependencies listed in the repository's
> requirements.txt. This can take several minutes - that is normal.

EXPECTED OUTPUT:
> ... Successfully installed fastapi-x.y.z xgboost-a.b.c ... (long list)

COMMAND (optional but recommended for development):
> pip install -r requirements-dev.txt

WHERE:
> PowerShell, .venv activated, project root

PURPOSE:
> Installs pytest, pytest-cov, httpx and ruff (the test and lint tools used
> by `make test` / `make lint` and section 30's checklist).

GDAL / rasterio note (Windows):
  requirements.txt says "gdal must be installed from the OS package manager
  on Windows/Linux (see docs/setup.md)". In practice rasterio and geopandas
  install fine from pip on modern Windows because they ship prebuilt wheels.
  If `pip install rasterio` or `pip install geopandas` FAILS, use the
  conda-forge route documented in docs/setup.md:
      conda create -n udt python=3.11
      conda activate udt
      conda install -c conda-forge gdal rasterio geopandas
      pip install -r requirements.txt

VERIFY the environment works:
COMMAND:
> python -c "import fastapi, uvicorn, xgboost, joblib, pandas, numpy; print('backend imports OK')"
EXPECTED OUTPUT:
> backend imports OK

(Optional, checks the geospatial stack too:
> python -c "import geopandas, rasterio, shapely; print('geo imports OK')")

To leave the environment later:
COMMAND:
> deactivate

Do NOT install random extra packages. Everything the project imports is
already covered by requirements.txt / requirements-dev.txt.

LINT:
COMMAND:
> npm run lint
WHERE:
> PowerShell, inside frontend\
PURPOSE:
> Runs oxlint (this project's linter - note it is NOT eslint) over the

EXPECTED OUTPUT:

PREVIEW (serve the production build locally):
COMMAND:
> npm run preview
WHERE:
> PowerShell, inside frontend\

 11. DOCKER SETUP
--------------------------------------------------------------------------------

The repository ships a docker-compose.yml at the project root with TWO
services (verified):

  SERVICE  : database
  CONTAINER: urban-twin-db
  IMAGE    : postgis/postgis:15-3.3   (PostgreSQL 15 + PostGIS 3.3)
  PURPOSE  : Optional PostGIS database. Runs the schema in
             database/schema/init.sql automatically on first start
             (mounted into /docker-entrypoint-initdb.d).
  PORTS    : 5432 (host) -> 5432 (container), configurable via POSTGRES_PORT

CRITICAL: the backend container mounts ./data and ./models from the host

up`. On the reference machine they exist. On a fresh GitHub clone they do not

(npm run dev) or by nginx from a production build (deployment/nginx/).

 12. DATABASE SETUP (POSTGRESQL / POSTGIS - OPTIONAL)
--------------------------------------------------------------------------------

Read this section BEFORE enabling the database. The default mode of the
system is "artifact-first": the API reads everything from data/ and models/
on disk, and you can skip this whole section. The database only becomes
active when UDT_DATABASE_URL is set.

--------------------------------------------------------------------------------
 12.1 What the database is
--------------------------------------------------------------------------------
From the repository (database/schema/init.sql + migrations):

  ENGINE    : PostgreSQL with PostGIS extension
  DATABASE  : urban_digital_twin
  USER      : admin
  PASSWORD  : password
  PORT      : 5432
  TABLES    : grid_cells (one row per 100 m cell, all engineered features +
              geometry), predictions (per-cell predictions per scenario),
              simulations (scenario sensitivity summaries),
              weather_daily, aqi_daily, schema_migrations (bookkeeping).

The schema is defined twice on purpose:
  - database/schema/init.sql        - auto-run by Docker on first start
  - database/migrations/0001_initial_schema.sql - applied by the migration
    runner (same content, versioned).

--------------------------------------------------------------------------------
 12.2 Does Docker initialize the database automatically?
--------------------------------------------------------------------------------
YES for the schema. docker-compose.yml mounts ./database/schema into
/docker-entrypoint-initdb.d, and PostgreSQL runs every .sql file there on the
FIRST initialization of an empty postgres_data volume. So:

  docker compose up -d --build     (or: docker compose up -d database)

creates the PostGIS extension and all tables automatically - on the first
start only. Afterwards the volume persists.

NO for the data. The tables are created EMPTY. To populate them from the
pipeline outputs, run the migration runner and the seed loader (12.3).

--------------------------------------------------------------------------------
 12.3 Migration and seed scripts (exist in the repository - use them)
--------------------------------------------------------------------------------
Two scripts are provided:
  - database/migrate.py             - applies database/migrations/*.sql in
                                      filename order; tracks applied files in
                                      schema_migrations.
  - database/seed/load_artifacts.py - loads the pipeline outputs:
                                        grid_cells  <- data/feature_engineering/
                                                       training_dataset.geojson
                                        predictions <- data/predictions/predictions.csv
                                        simulations <- data/outputs/reports/
                                                       sensitivity_analysis.csv

COMMAND:
> python database/migrate.py --url postgresql://admin:password@localhost:5432/urban_digital_twin

WHERE:
> PowerShell, .venv activated, project root. (Alternatively set the
> DATABASE_URL environment variable and omit --url.)

PURPOSE:
> Creates the schema (idempotent - it skips already-applied migrations).

EXPECTED OUTPUT:
> [apply] 0001_initial_schema.sql
> Migrations complete.

COMMAND:
> python database/seed/load_artifacts.py --url postgresql://admin:password@localhost:5432/urban_digital_twin

PURPOSE:
> Loads the grid cells, predictions and simulations from the pipeline files.
> Loading all 53,802 grid cells takes a minute or two.

EXPECTED OUTPUT:
> Grid features: 53802
> grid_cells loaded: 53802 rows
> predictions loaded: N rows
> simulations loaded: 7 rows
> Seed complete.

--------------------------------------------------------------------------------
 12.4 Switch the backend to database mode
--------------------------------------------------------------------------------
Edit the root .env (from section 10) and set:

  UDT_DATABASE_URL=postgresql://admin:password@localhost:5432/urban_digital_twin

Then restart the backend (in Docker: `docker compose up -d --build`; locally:
restart uvicorn).

--------------------------------------------------------------------------------
 12.5 Verify database connectivity
--------------------------------------------------------------------------------
COMMAND:
> Invoke-RestMethod -Method Get -Uri http://localhost:8000/api/health/database

PURPOSE:
> The API's own connectivity report.

EXPECTED OUTPUT (after seeding):
> enabled        : True
> grid_cells     : 53802

Direct check inside the container:
COMMAND:
> docker exec -it urban-twin-db psql -U admin -d urban_digital_twin -c "SELECT count(*) FROM grid_cells;"

EXPECTED OUTPUT:
>  count
> -------
>  53802

If UDT_DATABASE_URL is empty, /api/health/database returns:
> enabled : False, reason : "not configured"   (expected - database off)

--------------------------------------------------------------------------------
 14.1 What the model is (verified from the artifacts)
--------------------------------------------------------------------------------
  FILES        : models/best_model.pkl  (32.6 MB - used for inference)

                 backend serves inference from the .pkl, NOT the onnx)
  TYPE         : XGBRegressor (XGBoost gradient-boosted tree regressor)

--------------------------------------------------------------------------------
backend/services/serving.py (ServingContext):

 14.4 What happens if the model files are missing

 15. THE GIS PIPELINE
--------------------------------------------------------------------------------

This section documents the actual pipeline (gis-engine/). You only need it
if you want to re-download/reprocess the satellite data. On the reference
machine all outputs already exist, so this is OPTIONAL for running the app.

--------------------------------------------------------------------------------
 15.1 How it works (verified from gis-engine/main.py + config.py)
--------------------------------------------------------------------------------
The pipeline is an orchestrator that runs, in order:
  STAGE 1/2 - Sentinel-2 search + download (Microsoft Planetary Computer
              STAC, or Copernicus Data Space fallback)
  STAGE 2/6 - Sentinel processing: clip, NDVI, green cover, vegetation
              density, land cover, previews, stats
  STAGE 3/6 - Landsat 8/9: search, download, LST + heat classes
  STAGE 4/6 - DEM: download (Copernicus DEM GLO-30, no key), merge, clip,
              terrain derivatives (elevation, slope, aspect, hillshade,
              contours)
  STAGE 5/6 - NASA POWER weather: download, derive, plot, stats (no key)
  STAGE 6/6 - Air quality: observations (auto provider chain), interpolation
              (pykrige/IDW), AQI calculation

Feature engineering is a SEPARATE stage:
  gis-engine/feature_engineering/main.py builds the 100 m ML grid from the
  processed outputs -> data/feature_engineering/training_dataset.csv
  (53,802 cells, ~90 engineered features).

--------------------------------------------------------------------------------
 15.2 Running the GIS pipeline
--------------------------------------------------------------------------------
COMMAND:
> cd gis-engine
> python main.py

WHERE:
> PowerShell, .venv activated. IMPORTANT: run from inside gis-engine\ (the
> script imports `from config import Config` relative to that folder).

PURPOSE:
> Downloads and processes ALL datasets for the study area. Each stage skips
> work that already produced files (resumable). Add --force to redo
> everything.

USEFUL FLAGS (verified in gis-engine/main.py):
  --force             re-download and reprocess everything
  --skip-download     only process existing raw data
  --skip-process      only download imagery (skip Sentinel processing)
  --skip-landsat      skip the Landsat LST stage
  --skip-dem          skip the DEM terrain stage
  --skip-weather      skip the NASA POWER weather stage
  --skip-aqi          skip the air quality stage
  --cloud-max 15      max cloud cover percent for scene search
  --days 365          search lookback window in days

COMMAND:
> cd feature_engineering
> python main.py

WHERE:
> PowerShell, .venv activated, inside gis-engine\feature_engineering\

PURPOSE:
> Builds the 100 m ML training grid from the processed outputs.

--------------------------------------------------------------------------------
 15.3 Credentials and providers
--------------------------------------------------------------------------------
  - Sentinel-2: Microsoft Planetary Computer = default, NO credentials.
    Copernicus Data Space = fallback, needs CDSE_CLIENT_ID / CDSE_CLIENT_SECRET.
  - Landsat 8/9: Planetary Computer (no key) or USGS STAC.
  - DEM: Copernicus DEM public AWS bucket, NO key. SRTM via OpenTopography
    needs OPENTOPOGRAPHY_API_KEY (fallback only).
  - Weather: NASA POWER, NO key.
  - AQI: provider chain "auto" = sentinel-5p (needs CDSE credentials) ->
    openaq (needs OPENAQ_API_KEY) -> cpcb (best effort) -> demo (synthetic,
    clearly labelled). With no credentials at all, the pipeline can fall
    back to the labelled demo source (AQIConfig.demo_fallback = True).

--------------------------------------------------------------------------------
 15.4 Expected outputs and runtime
--------------------------------------------------------------------------------
Outputs land in data/raw, data/processed, data/statistics, data/plots and
logs/ (see section 13). Runtime: dominated by downloads - expect minutes to
an hour+ depending on your connection; VERIFY IN YOUR ENVIRONMENT. Failure
handling: exit code 0 = success, 1 = pipeline error, 2 = unexpected error,
130 = Ctrl-C. Completed files are reused on re-runs (skips existing work).

--------------------------------------------------------------------------------
 16.1 The training pipeline (ai-engine/main.py - 11 steps, verified)
--------------------------------------------------------------------------------
  1.  Load dataset + identify column roles
  2.  Remove leakage features            -> data/outputs/reports/leakage_report.json
  3.  Train/test split (80/20, seed 42)
  4.  5-fold cross-validation (RMSE, MAE, R2, MAPE)
  5.  Model comparison (6 models)        -> data/outputs/leaderboard.csv
  6.  Optuna hyper-parameter optimisation (100 trials)
  7.  Train final model                  -> models/best_model.pkl + .onnx
  8.  SHAP explainability                -> data/outputs/plots/SHAP/
  9.  Sensitivity analysis (green/building/tree/park/water)
 10.  Full-grid prediction               -> predictions.csv,
                                          Predicted_LST.{geojson,tif,png}
 11.  Evaluation                         -> data/outputs/metrics.json

> python main.py

WHERE:

PURPOSE:
> Trains and exports the model + all reports. This is the step that
> REGENERATES models/best_model.pkl. It takes tens of minutes (the reference
> run trained 6 models + 100 Optuna trials on 53,802 rows). You only need it

--------------------------------------------------------------------------------
 16.4 Nemotron (the natural-language AI - OPTIONAL)
--------------------------------------------------------------------------------
Architecture (verified):
    Frontend
      -> POST /api/ai/ask  {question, context}
      -> FastAPI builds a WHITELISTED context from REAL data
         (model status + client-supplied environment/urban/air/weather/
         prediction/scenario blocks)
      -> Nemotron/NVIDIA NIM (OpenAI-compatible chat completions)
      -> plain-text explanation returned

Rules enforced by the backend (backend/api/ai.py):
  - Nemotron NEVER computes numbers; it only explains the supplied context.
  - Missing data stays "unavailable" - nothing is fabricated.
  - The API key is read server-side only.

Nemotron is OPTIONAL: with no NEMOTRON_API_KEY the system runs normally and:
  GET  /api/ai/status -> {"available":false,"status":"configuration_required",...}
  POST /api/ai/ask    -> HTTP 200 {"success":false,"status":
                         "configuration_required","answer":null,...}
  The UI shows "Nemotron configuration required". Do NOT claim the AI is
  available when the key is not configured - the status endpoint tells the
  truth.

To enable: add NEMOTRON_API_KEY (and optionally NEMOTRON_BASE_URL /
NEMOTRON_MODEL / NEMOTRON_TIMEOUT_SECONDS / NEMOTRON_MAX_RETRIES) to the
root .env, then restart the backend. Verify with GET /api/ai/status ->
"configured" (availability is confirmed on the first real request).

 22. THE SEARCH SYSTEM
--------------------------------------------------------------------------------

Verified from frontend/src/services/geocoding.js:

  PROVIDER : OpenStreetMap Nominatim (https://nominatim.openstreetmap.org/
             search) - free, keyless. The provider is isolated behind
             searchPlaces(), so it could be swapped later.
  BEHAVIOUR:
    - DEBOUNCE: requests are delayed 400 ms after the last keystroke (no
      request per character).
    - MINIMUM QUERY: 2 characters (MIN_QUERY_LENGTH).
    - RESULT LIMIT: 6 results (RESULT_LIMIT).
    - CACHING: an in-memory Map cache (max 100 entries) - repeated queries
      are served instantly without a network call.
    - CANCELLATION: an AbortController aborts stale in-flight requests, so
      outdated results are never shown.
    - BIAS: a viewbox around the Bhubaneswar study area
      (85.70,20.08 - 85.95,20.45) makes local places rank first.
    - FLY-TO: selecting a result calls map.flyTo() to the place's
      coordinates (zoom 15-16 depending on bounding box) and drops a marker
      (handled in App.jsx handleSearchSelect).
    - FAILURE BEHAVIOUR: any error resolves to [] - the UI shows a graceful
      "search unavailable" state; it never throws.
  RATE LIMITS: public Nominatim asks clients to be polite (the frontend's
  debounce + small result limit + cache already comply with good-citizen
  usage). If you receive HTTP 429 responses, slow down searches; consider
  running your own Nominatim instance for heavy production use
  (VERIFY IN YOUR ENVIRONMENT - this project does not bundle one).


--------------------------------------------------------------------------------
 23. THE SCENARIO SYSTEM
--------------------------------------------------------------------------------

The 7 canonical scenarios are defined in ai-engine/config.py
(ScenarioConfig) and exposed by GET /api/simulation/scenarios (verified by
listing them from the running API):

  increase_green_10      Increase green cover by 10% (GreenCover, NDVI,
                         vegetation %, trees up; built-up down)
  increase_green_20      Same, stronger (+20%)
  decrease_buildings_10  Reduce building footprint & density by 10%
  decrease_buildings_20  Reduce building footprint & density by 20%
  increase_trees         Increase tree count and tree density (+50 trees,
                         +10 density)
  increase_parks         Increase park area / bring parks closer
                         (DistToPark x0.75, cooling index up)
  increase_water         Increase water bodies (DistToWater x0.75, water
                         pct up)

How a scenario run works (verified in backend/services/simulation.py and
ai-engine/scenario_simulator.py):
  BASELINE    : the full grid (or a sample) is predicted by XGBoost.
  PERTURBATION: the scenario's feature perturbations are applied; kinds are
                "add" (feature += value), "mul" (feature *= value),
                "min" / "max" (clamp feature).
  PREDICTION  : the perturbed grid is predicted by XGBoost.
  DELTA       : delta = scenario_prediction - baseline_prediction per cell
                (mean_delta_lst < 0 means cooling). No hardcoded
                temperature reductions.
  SPATIAL     : per-cell results are cached under data/outputs/scenarios/
                (<scenario>.json + <scenario>.geojson) and served by
                /api/simulation/results/{scenario}/cells and .../geojson.
  CACHING     : results are computed once and reused; ?refresh=true forces
                regeneration; caches invalidate automatically when the model
                or dataset changes (the cache manifest tracks the model
                state).

You can also run CUSTOM scenarios: POST /api/simulation/run with
{"perturbations":{"FeatureName":["add"|"mul"|"min"|"max", value]}} using
any of the 58 real feature names (see GET /api/prediction/features).
Unknown features/kinds are rejected with HTTP 400.


--------------------------------------------------------------------------------
 24. PERFORMANCE NOTES
--------------------------------------------------------------------------------

  - BROWSER-SAFE LAYERS: the map never loads raw rasters. It uses PNG
    overlays (frontend/public/overlays, ~24 MB total) with baked-in bounds,
    small web GeoJSON layers (frontend/public/3d-layers, ~1.8 MB) and
    pre-rendered terrain tiles (frontend/public/terrain).
  - LAZY LOADING: hotspots and cooling-potential GeoJSON are fetched ONLY
    when their chips are toggled on (App.jsx); the scenario overlay
    GeoJSON is fetched only when a scenario runs.
  - SCENARIO GEOJSON: the full-grid scenario layer has 53,802 features -
    it is fetched on demand and cached server-side; the response carries
    Cache-Control headers.
  - CACHING: layer files and heat outputs are served with
    "Cache-Control: public, max-age=3600"; scenario cell caches live in
    data/outputs/scenarios/; the fitted preprocessor is cached in
    data/predictions/serving/preprocessor.json so restarts skip refitting.
  - DOCKER: data/ and models/ are mounted read-only - no copies inside the
    image, no rebuild needed when data changes.
  - MODEL LOADING: the XGBoost model is deserialized ONCE on the first
    prediction request and reused for every request (lazy + cached).
  - API RESPONSES: heavy artifacts (GeoTIFFs, full-grid GeoJSON, CSVs) are
    streamed as files on demand; monitoring/environment endpoints compute
    small aggregates from disk.
  - WHY large raw GIS files must NOT go straight into the browser: a 100 m
    GeoTIFF or a 53,802-polygon GeoJSON is many megabytes of JSON/raster;
    fetching and parsing it in the browser would stall the page and exhaust
    memory on low-end devices. The architecture keeps big files on the
    backend and ships the browser small, pre-rendered representations.

 26. WINDOWS TROUBLESHOOTING
--------------------------------------------------------------------------------

Each entry: SYMPTOM / CAUSE / FIX / VERIFICATION.

1. SYMPTOM:  "'docker' is not recognized as the name of a cmdlet..."
   CAUSE:    Docker Desktop is not installed or its PATH entry is missing.
   FIX:      Install Docker Desktop (section 6.4) and restart PowerShell.
   VERIFY:   docker --version

   CAUSE:    Docker Desktop is installed but not started.
   FIX:      Start "Docker Desktop" from the Start menu; wait for the whale
             icon to report "Engine running", then retry.
   VERIFY:   docker info   (or: docker compose ps)

   CAUSE:    WSL2 not enabled/updated, or virtualisation off in BIOS.
   FIX:      wsl --install (Administrator); wsl --update; enable
             "Virtual Machine Platform" in Windows Features; reboot.
   VERIFY:   wsl --status  -> "Default Version: 2"

   CAUSE:    Another process (or a second backend) occupies port 8000.
   FIX:      Find and stop it: Get-NetTCPConnection -LocalPort 8000, then

             run the Docker backend and the local uvicorn at the same time.
   VERIFY:   uvicorn starts and http://localhost:8000/api/health responds.

--------------------------------------------------------------------------------
 27. HEALTH CHECKS (API VS DOCKER CONTAINER)
--------------------------------------------------------------------------------

There are three distinct "health" concepts - don't confuse them:

1. API liveness - GET /api/health
   Purpose: proves the FastAPI process is up and answering.
   Test:    Invoke-RestMethod -Method Get -Uri http://localhost:8000/api/health
   Expected: status = "ok" (always 200 while the process runs).

2. API readiness - GET /api/health/ready
   Purpose: proves the TRAINED MODEL and the key artifacts exist on disk
            (model_pkl, leakage_report, dataset_csv, metrics_json).
   Test:    Invoke-RestMethod -Method Get -Uri http://localhost:8000/api/health/ready
   Expected: status = "ready" + model_ready = true when all artifacts are
            present; "not_ready" + missing_artifacts list when not.

3. Docker container health (the "healthy" column in docker compose ps)
   The backend Dockerfile defines a HEALTHCHECK: every 30 s it fetches
   http://127.0.0.1:8000/api/health inside the container; 3 failures in a
   row mark the container "unhealthy". So "healthy" in Docker = the API
   liveness check inside the container passes (the process is up) - it does
   NOT prove the model artifacts exist. A container can be "healthy" while
   /api/health/ready reports "not_ready" (missing model) or while
   /api/model/info reports model_unavailable.

Test the container health explicitly:
COMMAND:
> docker inspect --format "{{.State.Health.Status}}" urban-twin-backend
EXPECTED OUTPUT:
> healthy

Also useful:
COMMAND:
> docker compose ps
(STATUS column shows Up ... (healthy) / (unhealthy))

 33. THE "ONE COMMAND" STARTUP
--------------------------------------------------------------------------------

There is no single command that starts the entire app, because the frontend
is intentionally not part of the Docker stack (the compose file starts only
backend + database). The shortest reliable sequence is TWO commands (plus
browser):

  Terminal 1 (backend):
  > cd F:\urban-digital-twin
  > docker compose up -d --build

  Terminal 2 (frontend):
  > cd F:\urban-digital-twin\frontend
  > npm run dev

Then open http://localhost:5173.

Alternatives that match the repository:
  - Makefile (if you have `make`, e.g. Git Bash / WSL):
      make docker-up      (same as docker compose up -d --build)
      make serve          (local uvicorn backend)
  - deployment/deploy.sh (bash, requires data/ to exist):
      ./deployment/deploy.sh        (docker build + compose up)
      ./deployment/deploy.sh --no-db (backend container only)
  - Full local mode (no Docker at all):
      .\.venv\Scripts\Activate.ps1 && uvicorn backend.main:app --reload
      (second window) cd frontend && npm run dev
